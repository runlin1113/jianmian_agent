第一章　项目概述
1.1　项目名称与释义
本项目中文名“简面”，英文名 Jianmian Studio，取自“简历”与“面试”两个词。名字背后是一个判断：一份简历的全部价值，是换来一次面试；而面试里被追问的内容，又几乎全部来自简历上写过的东西。把写作和面试放在同一个产品里，用户才有机会发现自己写下的哪一句经不起追问。
项目前身为“简面简历编辑平台”，由本人独立开发并已部署上线，具备模块化编辑、AI 润色、A4 预览与 PDF 导出四项能力。本次升级在该平台基础上接入智能体，文档中统一称“简面智能体”。
1.2　项目定位
简面是一套面向高校学生与初入职场者的简历撰写与面试准备工具。用户不必从空白文档起草，只需按模块填入自己的经历，由模型针对目标岗位改写，最终输出一份控制在一页 A4 内的文档；定稿之后，系统依据简历内容生成模拟面试题，把“写”和“面”接成一条线。
产品形态上刻意避开“一次生成一份完整简历交给用户”的做法。简历里的事实只有用户自己知道，模型能做的是组织与表达，不是无中生有。因此所有 AI 输出都落回可编辑的模块字段，用户随时能看、能改、能退回上一版。
1.3　项目背景
校招的初筛环节以简历为唯一材料。一个岗位收到的简历常在数百份以上，招聘方停留在单份简历上的时间以秒计算，能否在几秒内看到与岗位匹配的信息，直接决定是否进入下一轮。
高校课程体系里没有简历写作的训练。学生第一次写简历，多半参照学长学姐的模板或网上的范文。模板解决的是版式问题，解决不了内容判断：哪段经历该留、哪个数字该写、面向这个岗位应该突出什么。结果是大量简历长得一样，也都停在“参与”“负责”“协助”这类没有信息量的动词上。
大模型让段落写作的门槛降了下来，但通用对话框与简历之间还隔着一层工程问题：输出要结构化，页数要压到一页，姓名与时间这类事实不能被改写，结果要能直接排成 A4 版式。这些问题不属于模型能力，属于软件设计，恰好是可以由本项目解决的。
再看现有产品。在线简历站的排版已经做得很成熟，但把“针对岗位改写”和“面试准备”放在付费墙之后，源码不开放，数据存在云端。对价格敏感、又在意个人信息的学生群体，门槛偏高。
1.4　建设目标
（1）完成一套零部署成本的简历工具。单个 HTML 文件双击即可使用，导出的 PDF 符合 A4 规范，分页处不出现半页空白。
（2）把简历从“表单”变成“可对话的对象”。用户用自然语言描述需求，系统返回可编辑的结果，而不是一段需要用户自己搬运的文本。
（3）建立岗位知识与个人记忆两条数据线。前者让改写有依据，后者让多次迭代之间不丢失上下文。
（4）沉淀一套可复用的智能体工程做法。工具协议、结构化输出校验、事实字段保护、成本控制，这四点在本项目中都已遇到具体问题，并有对应解法。
第二章　市场与需求分析
2.1　市场机会
每年高校毕业生规模在千万级，加上实习生与社招新人，简历工具的潜在用户量并不小。但这类工具的使用是低频、强需求的：一个人一年可能只用两三次，可每次都在时间压力下完成。低频意味着用户不愿意为它付费订阅，强需求意味着他们愿意花时间找一个顺手的工具。这决定了产品的合理形态是免费、轻量、打开即用，而不是订阅制的重型 SaaS。
另一个变化来自模型侧。两年前做同类功能需要自己训练模型或调用昂贵的接口，现在按 token 计费的成本已经降到可以免费提供体验额度的水平。这给个人开发者留出了空间：一个人可以在业余时间做出可用的产品，成本由体验额度控制。

2.3　用户痛点
痛点是按用户动手写简历的顺序依次出现的，大致分四层。
（一）结构层：不知道简历由哪些部分构成
不清楚一份简历应该包含哪些部分，各部分的顺序和篇幅怎么分配。这一层最容易解决，给一套模块清单就够了。
（二）转化层：不会把做过的事写成结果
这是最普遍、也最难的一层。学生写“参与了 XX 课程设计，使用 Python 完成数据分析”，招聘方想读的是“清洗了多少条数据、用了什么方法、把什么指标从多少降到多少”。缺的不是经历，是把经历翻译成岗位语言的能力。这一层需要模型介入，也需要用户补出原始细节。
（三）对齐层：同一段经历投不同岗位，重点完全不同
投算法岗要突出模型选择与指标，投产品岗要突出需求判断与协作过程。多数学生只有一版简历，投所有岗位，于是每个岗位看到的都是“差不多但不是最合适”的那一版。
（四）市场层：不了解目标岗位的真实要求
包括关键词、能力模型与筛选标准。不清楚这些，就容易把时间花在次要的地方，比如反复调整字体，却不补一条量化结果。

第三章　产品设计
3.1　产品形态
产品是单页 Web 应用。界面分三栏：左栏是模块清单，可增删与排序；中栏是 A4 纸张的实时预览；右栏是当前模块的字段表单。顶部固定目标岗位输入与主要操作入口。
三栏结构不是随意定的。简历是所见即所得的文档，任何改动都应当在纸面上立刻看到结果，否则用户无法判断改得对不对；模块清单让用户始终知道这份简历还缺哪几块，避免写到一半忘记教育背景；右栏只放当前模块，把注意力收在一处，减少在长表单里迷路。
3.2　核心使用流程
整个流程六步走完，每一步都有明确产出。
（1）设定目标岗位。这个输入会进入后续每一次改写的提示词，是“岗位定向”的源头。
（2）添加模块并填写。八类模块可选，顺序可自定义。
（3）单模块润色。只重写当前模块的描述性字段，其余字段不动。
（4）整体压缩。把全部模块的文本一次性交给模型，压到一页 A4 以内。
（5）预览校对。在纸面上检查分页、留白与用词。
（6）导出 PDF。走浏览器打印，使用专用样式表。
升级为智能体后，第（2）步可以由对话代替：用户描述自己的经历，系统拆成模块并填好，用户再逐块确认。

3.4　从工具到智能体的五项能力升级
（一）对话式构建
现状是用户自己一块一块填。升级后，用户用一段话说明身份、目标岗位和主要经历，系统据此填出初稿，缺什么再反问。关键约束是初稿必须落回模块字段，而不是给一份文本让用户自行复制。
（二）记忆
记录目标岗位、项目库、技能、个人特征与表达偏好。记忆的作用不只是“记得住”，更在于减少重复输入：同一批项目在投第二个岗位时不必重填，系统知道用户习惯用分点还是段落。
（三）知识库与联网
岗位要求不能靠模型猜。知识库存放常见岗位的能力模型与关键词；联网用于获取最新的招聘要求与公司信息。两者的输出都只作为改写依据，不直接写进简历。
（四）简历解析
用户手上多半已有一份旧简历，格式是 PDF 或 Word。解析的作用是把它拆成八类模块，之后所有编辑能力都能作用在这份旧稿上。这是转化率最高的一项功能，也是技术上最容易低估的一项。
（五）面试官
依据定稿简历生成面试题，覆盖项目细节、技术选择、结果归因与岗位匹配。与通用题库的区别在于，题目必须挂在简历里写过的内容上，追问也沿着同一处往下挖。
3.5　设计原则
三条原则贯穿整个实现，每一条都对应一次具体的失败。
原则一，中间产物必须可编辑。早期考虑过让模型直接输出排版好的文本或 HTML，实现起来简单。但用户改一个字就要重新生成整段，几轮之后无法确认哪一版是自己要的。改为结构化字段后，模型的输出是一组键值对，用户在哪一项上不满意就只改那一项。
原则二，事实不交给模型。压缩功能上线初期出现过模型顺手改掉入职时间、把公司名写短的情况。此后在提示词里显式列出不可改动的字段，包括姓名、电话、邮箱、学校、公司、职位、起止时间、学历与专业，并要求只压缩描述性文字；回填时再做一次字段级比对。
原则三，先预览，后应用。任何改写结果都先在侧栏展示，用户确认后才写入简历，写入后仍可从历史快照退回。简历本身不是高压力文档，但错误的改动会直接影响投递，撤销成本必须足够低。

4.2　前端实现
前端是一个约 2700 行、11 万字符的单文件 HTML，没有框架、没有 CDN、没有构建步骤。这个选择有代价，状态管理和组件复用都要手写；收益是部署成本为零，用户把文件拖进浏览器就能用基础功能，也方便把整个应用作为一份文件分发和存档。
状态由一个对象承载：目标岗位、模板、主题与模块数组，序列化后写入 localStorage；历史快照单独存放，支持命名与恢复。渲染分两块，界面走常规 DOM，简历纸张按 A4 的物理尺寸 210×297mm 布局，单位统一用毫米，保证屏幕显示与打印输出一致。
主题通过 CSS 变量实现。六套配色只改一组变量，同时作用到界面与纸张，避免出现界面是这套色、导出却是另一套色的错位。
4.3　服务层与额度控制
服务层是一个一百余行的 Cloudflare Pages Function，解决三个具体问题。
一是密钥。站长的 API Key 只存在于服务端环境变量中，浏览器拿不到。二是跨域。前端请求同源的 /api/chat，由服务端转发到模型接口，浏览器不再直连模型域名，跨域问题从根上消失。
三是额度。限流键优先取 cf-connecting-ip，这个请求头由 Cloudflare 注入，客户端无法伪造；取不到时退化为前端生成的匿名标识。KV 中按客户端记录已用 token 与重置时间，采用 24 小时滚动窗口，默认每个客户端每日 60000 token。额度耗尽返回 402 与额度用完的错误码，前端据此引导用户填写自有 Key。
用户自备 Key 时，请求头携带 Authorization，服务层直接转发，不计额度也不写入 KV。这条分支既是成本控制手段，也是产品的一种表态：站长提供的是体验额度，长期使用应该用自己的账号。
这套设计有明确的取舍。以 IP 为粒度，同一局域网内的多个人会共享一份额度；但它的实现成本接近于零，且比本地存储里的标识更难伪造，对课程项目而言是合适的平衡。
4.4　提示词工程
每次调用由三段拼成：通用规则、模块专用规则与岗位上下文。
通用规则固定语气与长度，禁用空泛的行业套话，要求直接给结果、不带解释。模块规则按模块性质分别写：项目经历要求每句以强动词开头、提取可量化结果、分点呈现；自我评价要求删掉套话、提炼三个卖点；个人技能要求按技术类别合并同类项。岗位上下文注入用户填写的目标岗位与岗位需求描述，这是“定向”二字的全部来源。
输出密度分两档。精炼档要求每个字段一到两句、不超过 60 字；适中档两到三句。用户可切换，因为投递不同公司时对篇幅的容忍度不同。
整体压缩的提示词另有一段结构化要求：返回模块与字段的嵌套 JSON，明确列出不可改动的事实字段，同时限定总字数约 850 字、项目与实习每段保留两到三条要点。返回后按模块标识与字段名回填，解析失败则提示重试而不写入，避免把半截 JSON 写进简历。
4.5　分页与导出
A4 在 96dpi 下高约 1122.5 像素，渲染时逐块累加内容高度，超出即新建一张页面，最后按张数显示页数徽标。用户因此能实时看到“已经写到第二页”，而不是导出后才发现。
导出走浏览器打印，配一份专用样式表：页面设为 A4、边距归零，打印时把屏幕上的圆角、阴影与缩放全部展平，让多张页面自然分页。没有引入第三方 PDF 库，一是减少体积，二是避免中文字体嵌入带来的排版偏差。
4.6　数据存储与隐私
简历正文只存在浏览器本地，不上传服务器；经代理调用时，请求体在内存中转发给模型，不落盘、不写日志；站长密钥不下发到前端。
“数据不出本机”是这个产品相对在线简历站的明确取舍。代价是换设备后无法同步。后续如果做账号体系，会采用可选的端到端加密存储，而不是默认上传。
第五章　智能体方案设计
5.1　智能体结构
智能体分四层，层间单向依赖：上层调用下层，下层不感知上层。
图 2　智能体四层结构
这里需要说明为什么保留表单。简历是强结构数据，纯对话编辑在多轮之后容易失控：用户说“再简洁一点”，模型可能同时删掉了一条关键结果。表单是确定性的，对话负责补全与改写，表单负责承载与校正，两者分工而不是互相替代。
5.2　编排层与工具协议
编排层不做固定工作流，按用户意图动态选择工具序列。这一点与常见的工作流编排不同：用户可能说“帮我把项目经历改得像后端”，也可能说“我投这个岗位还缺什么”。前者是一次改写，后者要先取岗位要求再比对，工具序列完全不同。

5.3　记忆模块
记忆分两层。短期是当前会话的对话与简历状态；长期是结构化用户档案，包含目标岗位、项目库、技能清单、个人特征与表达偏好，另有历史版本用于回溯。
写入策略上有一个刻意的限制：只在用户确认后写入。模型在对话里会推断出一些信息，比如“这位用户偏向分点表达”，如果直接落库，几轮之后档案里就混进了猜测。读取时按相关性注入，不把整份档案塞进上下文，既省 token，也避免无关信息干扰当前任务。
5.4　知识库与联网检索
知识库存三类内容：常见岗位的招聘要求模板、岗位能力模型与关键词、简历写作的常见问题。检索按岗位名与技能标签做混合检索，关键词匹配保证召回，向量检索补充语义相近的表述，取前若干条注入提示词。
联网只用于获取实时信息，例如某公司当年的招聘页面。结果必须标注来源与获取时间，并且不直接写成简历内容，只作为改写依据。原因很直接：招聘信息会变，模型也没有能力判断网页内容是否过期。
5.5　简历解析
这是整个方案里最容易被低估的一环。流程分五步：文本抽取、版面分块、字段映射、置信度打分、低置信度字段交用户确认。
难点集中在版式。双栏排版的阅读顺序、表格里的时间与公司、图片化的文字，都会让“按行读”的朴素做法失效。对策是分档支持：Word 与可复制文本的 PDF 走完整解析；扫描件先做文字识别，并在结果上标注“需人工核对”，不假装解析成功。宁可让用户改两处，也不要给出看似完整、实则错位的模块。
5.6　面试官模块
现有版本已经能依据简历生成六到八道题，每题附考察点与追问方向，并给出准备建议。升级为智能体后增加三件事：多轮追问，按回答质量调整难度；结束时给出结构化反馈，分别评价技术深度、表达清晰度与项目真实性；对简历中可能夸大或含糊的表述做压力测试，让用户在真实面试前先遇到一次。
这一功能的边界要说清楚。它不能预测真实面试题，作用是让用户把简历上写过的每一句话都过一遍，确认自己答得上来。

第七章　推广与运营
7.1　推广思路
不做广投放。这类工具的用户集中在校园，决策又依赖身边人推荐，所以先从可触达的圈层开始，跑通一个再往外扩。
一是校内先行。在班级和社团内试用，收集真实简历作为测试样本，同时把使用中暴露的问题修掉。二是开源引流。代码放在公开仓库，说明文档写清部署方式与免费额度规则；会自己部署的人不多，但他们是口碑的起点。三是内容侧。把“简历怎么写”的具体问题写成短帖，比发产品广告有效，选题直接来自用户的实际提问。

第八章　可行性与成本
8.1　技术可行性
核心链路已经在现有平台跑通：模块化数据结构、提示词组装、结构化返回与回填、A4 渲染与导出，这些不需要重新设计，智能体是在其上增加一层编排。工具调用、结构化输出、长上下文是目前主流模型都已具备的能力，不需要自研模型。服务端成本接近于零，Cloudflare Pages 与 KV 的免费额度足以支撑课程项目与初期试用。
主要不确定性在简历解析的准确率。它取决于文件的版式质量，而不是模型能力，这一点已经通过分档支持与人工确认做了兜底。

第十一章　结语
简面要解决的问题很具体：让一个没写过简历的学生，在半小时内得到一份说得清楚、看得下去、经得起追问的简历。技术上它没有发明新东西，模型、托管、限流都是现成的，难点在于把这些零件按简历这个场景的约束组装起来：事实不能改，页数不能超，结果必须能编辑。
下一步的工作是把现有工具接上编排层，让它从“用户操作的工具”变成“能听懂需求的助手”。这也是本次课程设计希望验证的一件事：智能体的价值不完全取决于模型有多强，也取决于它是否愿意按一个具体场景的规矩做事。
