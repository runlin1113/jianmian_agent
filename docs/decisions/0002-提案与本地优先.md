# ADR 0002：AI 只产出提案，简历主数据留在浏览器

- 状态：已采纳
- 日期：2026-11-16
- 相关：架构书第 9.1、10.1、10.2、12.1 节

## 背景

"让 AI 直接改简历"最容易实现，也最容易出事：一次幻觉就把学校、时间、数字写进了最终稿，
而用户往往在导出之后才发现。另一个矛盾是"正文不出本机"与"要用云模型"。

## 决定

1. 模型输出统一为 `ChangeProposal{baseRevision, baseHash, operations[], expiresAt}`，
   **不是**新文档；
2. 采纳时服务端重查：run 所有权、提案到期、`revision` 相等、`content_hash` 相等、每条操作的 `before` 原值；
3. 在一份副本上**整批**应用，任何一步失败整批不写；
4. 路由表里**不存在** `POST /resumes`——简历正文只在浏览器 localStorage，服务端只保存 run 的工作副本，
   过期后由后台任务真正删除。

## 理由

- "提案"把不可逆的写入变成可审阅的对象，用户能逐项采纳、整批放弃；
- `baseHash` 挡住"生成期间用户在另一个标签页改了文档"这类覆盖事故；
- 没有云端主文档接口，"不持久化正文"就不是声明而是事实；想加同步必须显式设计并重新授权。

## 代价

- 前端必须自己维护 revision 与撤销栈（`state.js`），复杂度从服务端转到客户端；
- 跨设备继续编辑需要导出/导入 JSON，首版不做账号同步；
- 逐项采纳要求服务端支持子集应用（`opIndexes`），否则前端只能本地应用、失去服务端校验。

## 检验方式

`tests/test_api.py::test_proposal_rejects_mismatched_revision`、
`test_build_run_produces_proposal_and_applies_atomically`、
`tests/test_domain.py::test_proposal_batch_fails_when_one_operation_changes_fact`。
