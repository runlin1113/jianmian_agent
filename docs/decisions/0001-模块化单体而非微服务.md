# ADR 0001：模块化单体，而不是十四个微服务

- 状态：已采纳
- 日期：2026-11-16
- 相关：架构书第 6 章、第 14 章

## 背景

规格里有 M1—M14 十四个"模块"。字面上看像微服务，但其中只有 OCR 与复杂版式解析存在真实的
资源隔离需求（CPU/内存/崩溃域），其余都是同一份数据上的代码边界。

## 决定

首版是**模块化单体**：一个 FastAPI 进程 + 清晰的包边界（`domain/ports/adapters/workflows/application/api`）。
M1—M14 是代码边界与接口，不是部署单元。仅有解析器接口 `ParserAdapter` 预留了独立进程/worker 的可能。

## 理由

1. 十四个服务意味着十三次网络跳转、十三套部署与观测，课程场景下收益为零、故障面变大；
2. 领域规则必须"只有一份"。拆成服务后，字段权限、事实策略、提案校验很容易出现第两份实现；
3. 边界靠依赖方向保证（`api → application → workflows → domain`，`adapters` 只实现 `ports`），
   而不是靠 HTTP。真要拆某一块时，端口就是现成的接缝。

## 代价

- 单进程意味着单实例容量上限；横向扩展需要先解决 run 所有权与预算共享（见 ADR 0003）；
- 解析器与主进程共享 GIL，长任务需要 `anyio` 线程或独立 worker，首版用限时 + 上限兜住。

## 检验方式

`pytest` 中"同一份 GraphSpec 在两个执行器上跑出同样路径"的测试，就是"边界与框架无关"的可执行证明。
